The watch holds one key. Only the server talks to Todoist.

How Connect Todoist links a watch to someone's Todoist account, and what happens on every request afterwards and on Disconnect. The watch never sees a Todoist password or token, and the server never sees the password.

request response carries a secret (key, code, client secret or token)

The checks along the way

  • The code expires. A pairing code works for 15 minutes; after that the page says “This link has expired” and the watch shows “The code expired”.
  • The login is bound to one browser. state must match the cookie set by /connect/start. A callback link opened in another browser gets “Start again from the watch”, so a leaked or forwarded callback can't link a watch to the wrong Todoist account.
  • People check the code. A forwarded connect link would link the sender's watch to whoever logs in, as with any TV-style pairing. The page shows the code and says to continue only if it's on your own watch.
  • A stolen database isn't a key. The server stores only the hash of each device key and compares in constant time.
  • Refresh tokens are used once. Todoist replaces the refresh token on every refresh and revokes access if an old one is reused. D1 is strongly consistent, and the new tokens are saved only if no other request refreshed first.
  • Revoked access is visible. If Todoist refuses the refresh, the API answers 401 reconnect and the watch says “Connect Todoist again”.
  • Disconnect cleans up. The last watch of an account revokes the token at Todoist and deletes the user, sessions and minutes.

Owner shortcut: a request whose X-Api-Key equals the API_KEY secret skips D1 and uses the personal TODOIST_TOKEN. That's how the developer's own builds work.
